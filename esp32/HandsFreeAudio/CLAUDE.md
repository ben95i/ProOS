# HandsFreeAudio (ESP32 car Bluetooth receiver)

ESP-IDF firmware for an ESP32 that turns a Honda HR-V's head unit into a Bluetooth car kit. It plays phone music (A2DP sink, 44.1 kHz) and handles calls (HFP hands-free client, CVSD 8 kHz or mSBC 16 kHz) through an I2S DAC, picks up the driver's voice from an I2S microphone, and maps four touch pads to play-pause toggle / hang up, Siri / mic mute, next and previous. It advertises as **`Honda_HR-V`** (the log `TAG` is also the Bluetooth name).

This project stands alone inside ProOS: it is not a host, `login.sh` does not deploy it, and the ProOS code style in `CODESTYLE.md` applies (camelCase, verbose expressions broken into named intermediates, a comment on every function).

## Build and flash

ESP-IDF **6.0.1**, target `esp32` (the project was started under 5.5.3). There is no IDF, compiler or git in this workstation's shell, so builds happen elsewhere:

```bash
idf.py build flash monitor
```

Key build settings, all in `sdkconfig.defaults`: 4 MB flash (the LOLIN32's), console at 921600 baud (`idf.py monitor` follows it), unused Bluetooth profiles off (SPP, HFP Audio Gateway, OBEX client, AVRCP cover art), 2 host ACL links, Bluedroid and system task stacks sized from the `DIAG stack` readings (re-check those readings after any change that adds work to a task), Classic BT only (BLE off, and `initializeBluetoothStack()` releases the controller's BLE RAM with `esp_bt_controller_mem_release(ESP_BT_MODE_BLE)`), A2DP + HFP client + SPP, **SCO audio over HCI** (`BTDM_CTRL_BR_EDR_SCO_DATA_PATH_HCI`, `BT_HFP_AUDIO_DATA_PATH_HCI`, so call audio reaches the app as PCM, which is what the echo gate's reference needs), wideband speech (`BT_HFP_WBS_ENABLE`, mSBC), one SCO link, large single-app partition, -O2, 240 MHz. The lower block of that file is settings inherited from an older IDF and unrelated to audio.

| Function | GPIO | Notes |
| --- | --- | --- |
| DAC I2S (I2S0, master, stereo 16-bit) | BCLK 23 · WS 26 · DATA 25 | UDA1334A |
| Mic I2S (I2S1, master, mono 32-bit, left slot) | BCLK 21 · WS 32 · DATA 34 | Top 16 bits used (`>> 16`) |
| Touch pad Siri / mute (`TOUCH_PAD_SIRI_MUTE`) | 18 | TTP224 touch module, active high, pulled down, polled every 100 ms. During a call (or ringing) toggles `isMicMuted`: microphoneTask sends silence after all processing, and clears it when the call ends. | Touch pad Play-pause / end call (`TOUCH_PAD_PLAY_PAUSE`) | 4 | While a call is ringing or active, only hangs up or rejects it (`esp_hf_client_reject_call`); otherwise toggles play / pause from `isMediaPlaying`, which follows the phone's AVRCP play status notifications (`bluetoothAvrcpControllerCallback`), or the A2DP stream state for a phone without them |

Both I2S channels use `I2S_CLK_SRC_DEFAULT` (PLL), never APLL: APLL would not switch from 44.1 kHz to 16 kHz and the mic flooded the BT stack.

## How it works

### Tasks and callbacks

| Code | Runs on | Does |
| --- | --- | --- |
| `app_main()` | | NVS (erase and retry on bad partition), mutexes / buffers (aborts if any is NULL), touch pads, both I2S channels, filter coefficients, Bluetooth, tasks; then reconnects A2DP to the last phone saved in NVS (`bt_storage` / `last_bda`) |
| `touchPanelTask` | core 1, prio 5, 3072 B stack | Edge-detects the pads, sends AVRCP (`sendAvrcpButton`) or hangs up. Its stack reading is low only until a pad is pressed: 1536 B overflowed on a press, and 2048 B left 320 B in the car |
| `audioOutputTask` | core 1, prio 15 | Music: waits for 20 KB pre-roll in the 40 KB `a2dpRingBuffer`, then writes to the DAC; re-buffers on underflow; idles during a call |
| `microphoneTask` | core 1, prio 10, 6 KB stack | Sleeps on a task notification outside calls. In a call: reads 120-sample frames, high-pass 200 Hz → low-pass 7 kHz → `MICROPHONE_GAIN` → clamp → voice gate → `microphoneStreamBuffer`, then `esp_hf_client_outgoing_data_ready()` |
| `bluetoothA2dpSinkDataCallback` | Bluedroid | Music PCM into the ring buffer, never blocking (drops when full) |
| `bluetoothAppA2dpCallback` | Bluedroid | Saves the phone address on connect; SBC config → 44.1 kHz |
| `bluetoothHandsFreeClientCallback` | Bluedroid | Call state (`isCallActiveOrRinging`), audio connect → 8 / 16 kHz + call DMA profile + wake mic task + stop being discoverable; audio disconnect → 44.1 kHz + discoverable again |
| `bluetoothHandsFreeReceiveCallback` | Bluedroid | Far-end voice: optional trim, measures its level for the gate (`farEndPeakLevel`, a peak hold), mono → stereo, writes to the DAC with a 20 ms timeout |
| `bluetoothHandsFreeSendCallback` | Bluedroid | Hands the stack whole frames from `microphoneStreamBuffer` only, never partial |

Shared state is `volatile` flags (`isAudioPathOpen`, `isPlaying`, `isMicHardwareEnabled`, `isCallActiveOrRinging`, `enableHfpStereoMode`) and two mutexes, `txMutex` (DAC channel) and `rxMutex` (mic channel). `updateI2sSampleRate()` takes both, always tx then rx.

### Sample rate and DMA profiles

`updateI2sSampleRate(rate)` recalculates the filter and gate coefficients (`calculateFilterAlphas`), retunes the mic clock, and either rebuilds or retunes the DAC channel. DMA depth is fixed at channel creation, so the DAC channel is **deleted and rebuilt** (`switchTransmitProfile`) when switching between:

| Profile | Descriptors × frames | Queued | Why |
| --- | --- | --- | --- |
| Music | 6 × 960 | ~131 ms at 44.1 kHz | Smooth A2DP |
| Call | 6 × 60, 2 preloaded with silence | 15 ms at 16 kHz | Low call latency, one HFP frame per descriptor; preload gives the rate-matched SCO stream a cushion |

In a call the channel is always rebuilt, even on a mid-call codec change, so the queue is re-primed. The mic channel is enabled only during a call.

### Call audio rules that are load-bearing

- **Never call `esp_hf_client_connect_audio()`.** The phone (Audio Gateway) sets up SCO. Requesting it from here made the phone tear the link down mid-call: the speaker fell back to 44.1 kHz (sped-up audio) and the mic went silent. The long comment at the `CIND_CALL` handler explains it.
- Uplink backlog is held to 480 bytes (2 frames), dropping the oldest whole frames, so delay can't build up.
- Mic frames go into the stream buffer only whole: a partial write would shift 16-bit alignment for the rest of the call.
- Always poke `esp_hf_client_outgoing_data_ready()` after each mic frame, even a dropped one; skipping it stalled the uplink. The one exception is the back-off in `pokeUplink()`: after 8 frames in a row with no call to `bluetoothHandsFreeSendCallback()` (the SCO link has closed but the audio-state event hasn't arrived yet), it pokes only every 16th frame until a fetch is seen again. Without it, a call end logged 100+ `bta_hf_client_sco_co_out_data invalid air mode: 255` errors, whose UART output delayed the event further. The `DIAG mic` line shows `uplink fetches` (~133/s in a call) and `skipped`.
- Mic settle delay after call start is 80 ms (`HFP_MIC_STARTUP_DELAY_MS`), then the RX DMA is drained.
- Float samples are clamped before the int conversion (NaN and out of range both land in the clamp).
- Bluedroid callbacks must not block for long: DAC writes in a call time out after 20 ms, A2DP drops instead of waiting.

### Echo handling: `ECHO_MODE`

`ECHO_MODE` in `main.c` (default `ECHO_MODE_SPEEX`, overridable with `-DECHO_MODE=`) picks the uplink's echo handling: `ECHO_MODE_NONE` (0, straight mic path), `ECHO_MODE_GATE` (1, the voice-switched gate below) or `ECHO_MODE_SPEEX` (2). `AEC_GATE_ENABLED` and `AEC_SPEEX_ENABLED` are derived from it. `AEC_SPEAKER_ATTENUATION_DB` (−2 dB speaker trim) applies in every mode.

**SpeexDSP echo cancellation** (the "SpeexDSP echo cancellation" block in `main.c`, design and measurements in AEC-PLAN.md):
- **Reference:** `speakerSentCallback()` is the call-profile TX channel's `on_sent` interrupt. It copies the right channel of each descriptor the DAC finishes into `referenceRing` (1024 samples), with a release-ordered `referenceWriteIndex`. `micOverflowCallback()` (RX `on_recv_q_ovf`) counts dropped mic frames so the reference skips the same amount.
- **Alignment:** at call start and after a codec change, `startEchoCanceller()` creates the states, then drains the RX queue (`drainMicQueue()`), then starts reading the ring `AEC_REFERENCE_LEAD_SAMPLES` (120) behind its newest sample (`syncEchoReference()`). Creating before draining matters: frames that queue during the creation, drained first, put the reader ahead of the speaker for the whole call (car, 2026-10-22). `takeEchoReference()` re-aligns, counted as a `resync`, if the reader falls nearly a ring behind or gets ahead (a frame finds fewer samples than it needs).
- **Per frame:** HPF/LPF → int16 without gain → `cancelEcho()` (`speex_echo_cancellation()` then `speex_preprocess_run()`) → `MICROPHONE_GAIN` → uplink. Frames stay 120 samples at both rates.
- **Alignment is the same every call:** the speaker's `on_sent` and the mic's `on_recv` interrupts stamp each descriptor's end (`DmaStamp`, `esp_timer_get_time()`, a sequence count for the 64-bit time). `syncEchoReference()` waits for one mic frame to end (`waitForFreshMicFrame()`, which throws it away) and starts the reference at the sample that was playing then, interpolated from the speaker stamp, minus the lead. Before, the delay came out up to ~11 ms different per call, which a learned filter can't carry over.
- **Learned filter kept between calls:** destroying the states saves the echo filter (~23 KB at 16 kHz, `saveEchoFilter()` into `savedEchoFilter`, through the local addition in the vendored `mdf.c`); creating them loads it if it was saved at the same rate (`restoreEchoFilter()`) and frees it, so it never takes heap during a call. The `AEC on` line ends `filter from last call` or `learning from zero`. The first call after boot, and the first at a different rate, learn from zero (~10 s of the far end talking).
- **States:** the mic task creates them when call audio starts and destroys them at call end, at call rates only, after checking the heap leaves `AEC_HEAP_RESERVE_BYTES` (20 KB), counting a saved filter as heap coming back. SpeexDSP doesn't check its own allocations, so that check is what keeps a small heap from crashing. Without states, the mic passes through.
- **Log:** `--- AEC on | 16000 Hz | 120 ms tail | 57K | heap left …K | filter from last call ---` at call start, or `--- AEC off: …` if the heap was short. With `DIAG_LOG_ENABLED`, a `DIAG aec` line each second shows ERLE over far-end frames, reference samples received (`ref in`, about the sample rate each second) and short/resync counts, call samples the DAC queue refused (`dac refused`, 0 normally), mic overflows and live SpeexDSP allocations (61 in a 16 kHz call).

### Voice-switched echo gate (`ECHO_MODE_GATE`)

Not an echo canceller: half-duplex ducking. Once per mic frame (7.5 ms at 16 kHz) it compares the far-end level (what was sent to the DAC) with the mic level; when the far end talks and the mic is not above the expected echo by a margin, the uplink glides down to `AEC_DUCK_DEPTH_DB`, interpolated per sample so it doesn't click. A slow far-end release (180 ms) spans the 20–50 ms acoustic loop, so no delay line is needed. All constants are `#define`s in the tuning block at the top of `main.c`, converted to per-frame coefficients in `calculateFilterAlphas()` so they hold at both 8 and 16 kHz.

| Switch | Current | Effect |
| --- | --- | --- |
| `ECHO_MODE` | `ECHO_MODE_SPEEX` | Which echo handling is compiled in (above) |
| `DIAG_LOG_ENABLED` | 1 | Call-time budget for the echo canceller: once a second mic frame time against the frame period, heap free / largest block / minimum, mic task stack left (`DIAG mic …`, which also counts `empty` uplink fetches: no whole frame queued, a click at the far end); then the crackle counters (`DIAG audio spk underruns N full-scale N | mic clipped N of N`: speaker descriptors played as silence, downlink samples the phone sent already clipped, mic samples clipped by `MICROPHONE_GAIN`), all 0 in a clean call; every 10 s each core's idle share and the busiest tasks (`DIAG cpu …`) and every task's unused stack, tightest first (`DIAG stack free B: …`); heap at boot and at call start (`DIAG heap …`). Printed by `diagnosticsTask` (core 1, priority 2), never by the mic task. Needs `CONFIG_FREERTOS_USE_TRACE_FACILITY` and `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS` |

Current tuning: `AEC_FAR_ACTIVE_LEVEL` 500, `AEC_ECHO_COUPLING_DB` −20, `AEC_NEAREND_MARGIN` 6, `AEC_DUCK_DEPTH_DB` −32, `AEC_FAR_RELEASE_MS` 180, `AEC_DUCK_RECOVERY_MS` 120, `AEC_SPEAKER_ATTENUATION_DB` −2. They were tuned in the car; the tuning log, the calibration assistant and `GATE-TUNING-GUIDE.md` that did it were removed (in git history), since the gate is being replaced (AEC-PLAN.md) and only stays for A/B comparison and as a fallback. `AEC_ECHO_COUPLING_DB` is relative to the mic after `MICROPHONE_GAIN`, so changing the gain or the speaker trim moves it.

## Testing: the simulator

`sim/` is a host simulator that `#include`s `main/main.c` unmodified and runs it on a Linux PC against mocks: `stubs/espmock.h` / `espmock.c` provide FreeRTOS tasks as pthreads, I2S with a DMA descriptor model (a write releases a descriptor only when it is full), Bluedroid callbacks, NVS and a virtual clock (below). Every other header in `stubs/` (`freertos/task.h`, `driver/i2s_std.h`, `esp_bt.h` …) is a one-line forwarder to `espmock.h`. `sim.c` adds a simulated I2S clock, a car-cabin echo model (140-tap impulse, 180-sample delay), synthetic far / near speech, a phone thread that plays the phone and Bluedroid's SCO path (below), an optional CPU cost model (below), and the report.

Needs `gcc` (or any C11 compiler with pthreads) and `make`; there is neither in this workstation's shell, so the user runs it from their own terminal:

```bash
make -C sim test
```

`make -C sim` only builds `sim/build/sim` and `sim/build/speexcheck`; `make -C sim speexcheck` builds and runs the SpeexDSP check alone (`make test` runs it last): for 16 kHz with 120 and 90 ms tails and 8 kHz with 120 ms, it prints the bytes the echo canceller and preprocessor allocate, echo reduction on a synthetic echo with and without the residual suppression, host µs per frame, and fails if any allocation is left after the states are destroyed. The sim and the check compile SpeexDSP with the same defines as its `CMakeLists.txt`; keep the two in step; `make -C sim run S=4` runs one scenario (`V=1` adds the firmware's log); `./sim/build/sim <scenario> [verbose] [nocost]` runs it directly (a number in place of `verbose` is the old speedup argument, ignored). `COST=0` on `make test` or `make run` runs without the CPU cost model (`nocost`). `MAIN_DIR=<folder>` builds against `<folder>/main.c` instead of `main/main.c`, for a throwaway experiment that leaves the firmware alone (a copy under `sim/experiments/`, which git ignores and `make clean` leaves); add `-B` to make when switching, or the old binary stays.

**Virtual clock.** Every simulated thread (the firmware's tasks, `sim.c`'s hardware, phone, A2DP and talker threads, and `main`) is a pthread started through `simThreadCreate()` (`xTaskCreatePinnedToCore()` uses it), but only one runs at a time. A thread gives up its turn only inside a blocking mock (`vTaskDelay`, `simSleepUs`, semaphores, task notifications, the ring buffer, I2S reads and writes); the next ready thread runs, and when none is ready the clock jumps to the earliest deadline. So results don't depend on the PC's speed or load (the old real-sleep clock collapsed scenarios 1 and 10 on a busy host), and a run repeats exactly. What that costs: code between two blocking calls takes no virtual time unless the CPU cost model charges it (below), tasks switch only at blocking calls, so a race that needs preemption mid-function can't happen, and priorities are ignored. A run that can't finish stops itself and prints every thread's state (running, sleeping until when, or waiting on what since when) and the firmware's handle addresses: a loop that never blocks (no switch for 20 real seconds), a thread waiting over 10 simulated seconds for a mutex (the firmware only holds them for milliseconds), every thread waiting with no deadline, or a run past 15 simulated minutes. Ctrl+C prints the same dump. A blocking mock must wait with `simWaitObject()` and be woken with `simWakeObject()` by whatever changes its condition. Giving a semaphore that a thread waits on hands it straight to the longest waiter, as the ESP32's second core or preemption would; otherwise `microphoneTask`, which gives `rxMutex` and takes it again every frame, starved a codec swap in scenario 4.

**CPU cost model** (on by default, `nocost` turns it off). Timing bugs that need the board's processing time can't show on a clock where code takes none, so `sim.c` charges virtual time for the firmware's known costly work, with figures from the board: `simSpendCpuUs()` (`espmock.c`) makes the calling thread sleep that long, so the other threads run meanwhile, as on the ESP32's other core or by preemption. `main.c` is not modified: before including it, `sim.c` renames its calls to `speex_echo_state_init`, `speex_preprocess_state_init` and `speex_echo_cancellation` with macros, to wrappers that call the real function and then charge it.

| Work | Charged | Source |
| --- | --- | --- |
| One mic frame | `SIM_COST_MIC_FRAME_US_16K` 4300 µs at 16 kHz, after `speex_echo_cancellation()`; scaled by the rate, so 2150 µs at 8 kHz | Car, 2026-10-21 and 22: `DIAG mic` average 4.3–4.4 ms. The 8 kHz figure is an estimate (no CVSD call measured) |
| Creating the canceller and preprocessor | `SIM_COST_CREATE_US_PER_KB` 85 µs per KB they allocate: ~4.9 ms at 16 kHz (57.5 KB), ~2.6 ms at 8 kHz | Not measured, only known to be a few ms; `esp_timer_get_time()` around `createEchoCanceller()` on the board would settle it |

Override a figure with `make -B -C sim test CFLAGS="-O2 -g -DSIM_COST_MIC_FRAME_US_16K=5700"`. With the model on, the `DIAG mic` frame time in the verbose log reads the charged figure. The creation cost is what lets the simulator show the half-filled reference of the second car test: built with the alignment code that was in the car (`startEchoCanceller()` draining before creating, `syncEchoReference()` taking the newest written sample without waiting for a fresh mic frame, and no re-align when ahead in `takeEchoReference()`), frames queue during the creation on some calls, and those calls run misaligned to the end: scenario 3 had a short reference on 16 of its 40 calls (worst 7800 samples/s) and scenario 1's call 7996/s, the car's ~8000; suppression fell to 5.5 and 8.5 dB. With `nocost` no call had it. Today's code with only the order reverted had none and no resyncs, since `syncEchoReference()` waits for a fresh mic frame (2026-10-22).

**The phone and Bluedroid's uplink.** The phone thread plays the BTU task: every 7.5 ms (± the scenario's ppm) it delivers one downlink frame through the receive callback, whose DAC write can block it, then sends one uplink frame over the air. Uplink frames come to the air the way ESP-IDF's Bluedroid fetches them (`bta_hf_client_sco_event()`, the CI data event): each `esp_hf_client_outgoing_data_ready()` wakes it, and it fetches whole frames from `bluetoothHandsFreeSendCallback()` until a fetch comes back short, queueing each for the air (Bluedroid stops early only at a queue depth of 20, `BTM_SCO_XMIT_QUEUE_HIGH_WM`). So a poke that finds one frame costs two fetches, the second one empty, as on the board (~270 fetches a second in an mSBC call, half of them empty), with or without the cost model. Without SCO audio a poke fetches nothing, as Bluedroid's `invalid air mode` path does.

| Scenario | Exercises |
| --- | --- |
| 1 · 2 | 180 s call with the phone clock at +60 / −60 ppm |
| 3 | 40 short calls with music between them |
| 4 | Codec swaps mid-call (CVSD ↔ mSBC without a disconnect) |
| 5 | 40 abrupt SCO losses |
| 9 | DAC byte accounting over one 30 s call |
| 10 | Far-end-only 60 s call (gate suppression in isolation) |

Each report gives: whether the CPU cost model was on; calls, uplink frames sent over the air as a share of line rate, worst uplink gap, longest stretch of near-end speech the far end could not hear (`deadRun`), DAC queue average / max in ms, DAC underruns, mic overruns, live I2S channels (should be 2); echo suppression in dB while only the far end talks; downlink rate; uplink fetches and empty fetches a second, air intervals with no frame queued, silent 200 ms windows while the near end talks; with the canceller, the calls on which a mic frame found too little reference (with the worst rate of zero-padded samples a second; ~8000 in the misaligned car call) and the re-alignments (`resync`); and any warnings or errors the firmware logged, grouped by message.

Known limits: `main.c` logs some `uint32_t` values with `%lu` (correct on the ESP32, where `uint32_t` is `unsigned long`), which can print wrong numbers in verbose mode on a 64-bit PC; A new IDF call in `main.c` needs its declaration in `espmock.h` and a body in `espmock.c` before the simulator builds again. In the simulator the `DIAG` heap figures are fixed placeholders, the stack figure is the whole stack, the frame time is what the cost model charges (0 with `nocost`), and task CPU shares are host-thread CPU time (no idle tasks, so idle reads 0%); only the task ranking means anything there. Final checks are in the car, with the logging switches above.

## Working on it
